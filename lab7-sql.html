Lab 7 · Week 7

SQL: Cleaning Data at the Source

Lab session · 80 minPairs with Chapter 6 · What Data Is →

Cascadia's controller has been sitting on a dirty sales export all quarter. Cleaning it by hand in Excel would take a whole session: removing duplicates, trimming spaces, fixing dates, converting text back into numbers. Today you will do the same job in SQL, and it will take you about six functions.

That comparison is the point of this lab. Cleaning data is the least glamorous work in the field and by far the most common, so the tool you use for it matters more than almost anything else you learn this quarter.

Where this framework comes from

The six steps below follow a widely shared SQL data-cleaning cheat sheet by data analyst Jess Ramos. It is a good summary of how working analysts actually approach a messy table, which is why we are using it rather than something invented for a textbook.

The schema

The database has the co-op's seven clean tables plus one deliberately messy one. You will work mostly in sales_raw.

sales_raw(sale_id, sale_date, store, category, state, quantity, unit_price, member_id) · stores(store_id, store_name, region, opened_year, square_feet) · suppliers(supplier_id, supplier_name, country, lead_time_days) · products(product_id, product_name, category, supplier_id, unit_cost, list_price) · members(member_id, first_name, last_name, city, state, member_type, join_date) · sales(sale_id, sale_date, store_id, product_id, member_id, quantity, unit_price) · inventory(store_id, product_id, quantity_on_hand, reorder_point) · used_gear(item_id, product_id, store_id, condition, listed_price, date_listed, date_sold)

Part 1Why the data is not in Excel

Everything you have touched this quarter has been a spreadsheet, so it is worth saying plainly: no real company keeps its operating data in Excel. Cascadia's registers do not write to a workbook. They write to a database, and the difference is not cosmetic.

A spreadsheet is one grid, edited by one person at a time, that tops out around a million rows and lives in a file someone can move, break, or email around. A relational database is different on every count. It is a set of tables living on a server. Hundreds of registers and websites write to it at the same moment. It holds effectively unlimited rows. And you read it by asking questions in SQL, not by scrolling.

The word relational is the important one. Look at the schema box above: the sales table does not contain store names. It contains a store_id, a number pointing at one row of the stores table, where the name, region, and square footage live exactly once. That pointer is called a foreign key, and the column it points at, the one that uniquely identifies each row, is a primary key.

Why build it that way? Because facts should live in one place. If Bellingham's name were spelled out on all of its sales rows and the co-op renamed the store, someone would have to fix thousands of rows and would miss some, and you have already seen this movie: it is exactly how the state column in sales_raw ended up with fourteen spellings. Storing each fact once and pointing at it is the cure for the disease you are about to spend this lab treating. Monday's lecture calls this normalization; today you get to feel why it exists.

The one-sentence version

Excel is where analysis happens. A database is where the truth lives. The skill this lab teaches is going to the truth directly.

Part 2Follow along: six steps for cleaning any table

Every query in this part is printed for you. Type it into the sandbox above (typing, not pasting, is how the syntax gets into your hands), press Run, and enter what comes back. The last three checkpoints then hand the keyboard fully to you.

1. Understand the data

Never clean anything before you have measured what is wrong with it. Your first job is a damage report, not a repair.

SELECT COUNT(*) FROM sales_raw; tells you how big it is. SELECT COUNT(DISTINCT sale_id) FROM sales_raw; tells you how many real orders there are. If those two numbers disagree, you have duplicates, and you now know exactly how many. SELECT * FROM sales_raw LIMIT 10; shows you what the rows actually look like, which is always worth doing before you assume anything.

2. Standardize formats

The same value written five ways is five values as far as the database is concerned, and that quietly ruins every count and every GROUP BY you write afterward.

  • trim(store) removes leading and trailing spaces
  • lower(store) or upper(store) forces one casing
  • replace(unit_price, '$', '') strips a stray character
  • CAST(replace(unit_price,'$','') AS REAL) turns the cleaned text back into a number you can add up

Try it: run SELECT COUNT(DISTINCT store) FROM sales_raw; and then the same query wrapped in lower(trim(...)). The co-op has eight stores. Whatever number the first query gives you is the size of the problem.

3. Identify missing values

Missing is not the same as zero, and it is not the same as empty text. SQL has a separate idea for it: NULL.

Find them with WHERE quantity IS NULL. Note carefully that = NULL does not work and will silently return nothing, because nothing is equal to NULL, including NULL. That trips up nearly everyone once, and it will be on Exam 2.

4. Handle and recode values

Two different jobs live here. Handling a missing value means deciding what to put in its place: COALESCE(quantity, 0) returns the quantity, or zero when it is NULL. NULLIF(state, '') does the reverse, turning empty text into a proper NULL so it stops masquerading as a real value.

Recoding is harder and no function can do it for you. Look at the state column:

SELECT DISTINCT state FROM sales_raw ORDER BY 1;

You will find WA, wa, Wash., and Washington all describing the same state. Cleaning the text with trim and upper gets you partway, but only a person knows that "Wash." means Washington. That judgment goes into a CASE expression:

SELECT CASE
         WHEN upper(trim(state)) IN ('WA','WASHINGTON','WASH.') THEN 'WA'
         WHEN upper(trim(state)) IN ('OR','OREGON','ORE.')      THEN 'OR'
         ELSE 'ID'
       END AS state_clean,
       COUNT(*)
FROM sales_raw
GROUP BY state_clean;

This is the step where a human has to know the business. It is also, not coincidentally, the step that is hardest to automate away.

5. Identify duplicates

Group by whatever should be unique and keep only the groups that appear more than once:

SELECT sale_id, COUNT(*)
FROM sales_raw
GROUP BY sale_id
HAVING COUNT(*) > 1;

HAVING filters groups the way WHERE filters rows. You need it here because you are asking a question about the group, not about any single row.

6. Remove duplicates

Number the rows within each group, then keep number one:

SELECT sale_id, quantity, unit_price
FROM (
  SELECT sale_id, quantity, unit_price,
         ROW_NUMBER() OVER (PARTITION BY sale_id ORDER BY sale_id) AS rn
  FROM sales_raw
)
WHERE rn = 1;

PARTITION BY restarts the numbering for each sale_id, so every real order gets a row 1 and its copies get 2, 3, and so on.

A warning about cheat sheets

Published examples of this pattern often end with QUALIFY rn = 1, which is shorter and reads better. It will fail in this sandbox, and in SQLite, MySQL, and PostgreSQL, because QUALIFY exists only in Snowflake, BigQuery, and a few others. Try it and read the error. This is worth experiencing once: SQL is a standard that every database extends differently, and code you copy from the internet may be written for a database you are not using.

The payoff: tables that connect

Cleaning one table is half the story. The other half is that tables answer questions together. The pattern is JOIN:

SELECT s.store_name, SUM(sa.quantity * sa.unit_price) AS revenue
FROM sales sa
JOIN stores s ON s.store_id = sa.store_id
GROUP BY s.store_name;

Read the ON clause out loud: connect each sales row to the stores row whose primary key matches its foreign key. Every SUMIF you wrote in Lab 3 asked one question of one table; a JOIN asks one question across two tables at once, and the last two checkpoints ask you to make that move.
