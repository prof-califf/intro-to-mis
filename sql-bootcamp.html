SQL Bootcamp: From One Query to Real Analysis

About 3 to 5 hours, at your own paceBuilds on Lab 7 →

Lab 7 showed you that you can ask a database a question. One week is enough to learn that, and not enough to learn what analysts do with SQL every day. This bootcamp is the rest of it: joining several tables at once, grouping and filtering groups, working with dates, labeling rows, breaking a hard question into steps, and comparing each row with the ones around it. You work on the same Cascadia database, in your browser, with nothing to install.

The SQL cheat sheet: every word this lab uses, plus a few more, all runnable


Every example below runs in the sandbox as written. The four groups are the order the steps use them
in. Come back here whenever a word looks unfamiliar.


1. Getting data out: SELECT and FROM. Every query starts with these two. The star
means all columns; naming columns keeps the result narrow; DISTINCT means each value once.


SELECT * FROM stores;
SELECT store_name, region FROM stores;
SELECT DISTINCT category FROM products;


2. Keeping some rows: WHERE. Compare with =, >, <, and <> (not equal).
LIKE matches a pattern, where % means "anything here." AND needs both conditions true; OR needs either.
Text goes in single quotes; numbers do not.


SELECT product_name, list_price FROM products WHERE list_price < 30;
SELECT product_name FROM products WHERE product_name LIKE 'Ridgeline%';
SELECT COUNT(*) FROM sales WHERE store_id = 4 AND quantity > 2;
SELECT COUNT(*) FROM sales WHERE store_id = 5 OR store_id = 8;


3. Sorting and stopping: ORDER BY and LIMIT. ORDER BY sorts smallest first unless
you add DESC. LIMIT stops after that many rows, and it always goes last.


SELECT product_name, list_price FROM products ORDER BY list_price DESC LIMIT 5;


4. Adding things up: COUNT, SUM, AVG, MIN, MAX, and GROUP BY. On their own, these
turn a whole table into one number. Add GROUP BY and you get one number per group, which is a pivot
table in words.


SELECT AVG(list_price) FROM products;
SELECT MIN(list_price), MAX(list_price) FROM products;
SELECT category, COUNT(*) FROM products GROUP BY category;
SELECT store_id, SUM(quantity * unit_price) FROM sales GROUP BY store_id;


Then JOIN, which Steps 5 and 6 teach on their own, because it is the one idea here
with no spreadsheet equivalent.

2Joins: three tables at once


About 45 minutes. A sales row says product_id = 129, not "Touring Ski
Package." To get names, you join tables on the keys they share. You can chain as many
joins as you need, and short names after each table, called aliases, keep the query
readable:


SELECT s.sale_date, p.product_name, st.store_name
FROM sales s
JOIN products p ON s.product_id = p.product_id
JOIN stores st ON s.store_id = st.store_id
LIMIT 10;


Read it from the middle out: start with sales, attach each sale's product, then attach its store.
Now add a third hop. Suppliers do not connect to sales directly. They connect through products:


SELECT su.supplier_name, SUM(s.quantity * s.unit_price) AS revenue
FROM sales s
JOIN products p ON s.product_id = p.product_id
JOIN suppliers su ON p.supplier_id = su.supplier_id
GROUP BY su.supplier_name;


Module 2Following the keysAnswer goes in Checkpoint 2





A plain JOIN keeps only rows that match on both sides. Sometimes the question is about what is
missing: customers who never came back, products that never sold. For that you need a
LEFT JOIN, which keeps every row from the first table and leaves blanks where nothing
matched. Then you keep only the blanks:


SELECT m.first_name, m.last_name
FROM members m
LEFT JOIN sales s ON m.member_id = s.member_id AND s.store_id = 3
WHERE s.sale_id IS NULL;


That lists the members who have never bought anything at Tacoma (store 3). Notice where the store
condition goes: inside the ON, not in a WHERE. Put it in the WHERE and the blanks disappear, and so does
your answer.


Module 2Finding what is missingAnswer goes in Checkpoint 3





3Groups: GROUP BY and HAVING


About 40 minutes. GROUP BY collapses many rows into one row per group, and SUM, COUNT, and AVG work
inside each group. You used it in Lab 7 for revenue by store. Here it is by category:


SELECT p.category, SUM(s.quantity * s.unit_price) AS revenue
FROM sales s
JOIN products p ON s.product_id = p.product_id
GROUP BY p.category
ORDER BY revenue DESC;


Module 3Revenue by groupAnswer goes in Checkpoint 4





WHERE and HAVING both filter, at different moments. WHERE filters rows before they are
grouped. HAVING filters groups after they are formed, which means it can use COUNT and
SUM. This lists members with at least 40 purchases (one purchase is one row in sales):


SELECT member_id, COUNT(*) AS purchases
FROM sales
WHERE member_id IS NOT NULL
GROUP BY member_id
HAVING COUNT(*) >= 40
ORDER BY purchases DESC;


Try it without the WHERE line and look at the top row. Sales with no member attached all land in one
group with a blank member_id, and that group is large. Leave that line in.


Module 3Filtering groupsAnswer goes in Checkpoint 5





4Dates and CASE


About 40 minutes. Dates in this database are text written as year-month-day, like
2025-03-14. That order sorts correctly, and
strftime pulls out a piece of it. '%m' is the
month:


SELECT strftime('%m', sale_date) AS month, COUNT(*) AS sales
FROM sales
GROUP BY month
ORDER BY month;


Module 4Revenue by monthAnswer goes in Checkpoint 6





CASE labels rows by a rule, the way IF did in Excel. This sorts sales into two
sizes:


SELECT CASE WHEN quantity >= 3 THEN 'bulk' ELSE 'single' END AS size,
       COUNT(*) AS sales
FROM sales
GROUP BY size;


CASE can also sit inside SUM, so you can add up only the rows that meet a rule while still dividing
by the total. That is how you get a share in one query:


SELECT 100.0 * SUM(CASE WHEN quantity >= 3 THEN quantity * unit_price ELSE 0 END)
       / SUM(quantity * unit_price) AS pct_from_bulk
FROM sales;


Module 4A share with CASEAnswer goes in Checkpoint 7





5Subqueries and CTEs: one question in steps


About 40 minutes. A subquery is a query inside another query. The inner one runs
first and hands its answer to the outer one. Here the inner query finds the average unit cost, and the
outer one keeps the products above it:


SELECT product_name, unit_cost
FROM products
WHERE unit_cost > (SELECT AVG(unit_cost) FROM products);


Module 5Above averageAnswer goes in Checkpoint 8





When a question needs several steps, a CTE (common table expression) lets you name
each step and use it like a table. It starts with WITH. This one computes
revenue per store first, then joins it to the stores table:


WITH store_rev AS (
  SELECT store_id, SUM(quantity * unit_price) AS revenue
  FROM sales
  GROUP BY store_id
)
SELECT st.store_name, r.revenue
FROM store_rev r
JOIN stores st ON r.store_id = st.store_id
ORDER BY r.revenue DESC;


Seattle is on top, but Seattle is also the biggest store. Chapter 6's question applies: is total
revenue the right measure? Divide by st.square_feet and the ranking
changes.


Module 5The fairer measureAnswer goes in Checkpoint 9





6Window functions: comparing a row with its neighbors


About 45 minutes. GROUP BY collapses rows. A window function does a calculation across
related rows but keeps every row, so you can see each one next to its rank, its running total, or the
row before it. The window is described after OVER:


SELECT st.store_name,
       SUM(s.quantity * s.unit_price) AS revenue,
       RANK() OVER (ORDER BY SUM(s.quantity * s.unit_price) DESC) AS rnk
FROM sales s
JOIN stores st ON s.store_id = st.store_id
GROUP BY st.store_name;


Add PARTITION BY and the ranking restarts inside each group. This ranks
every product within its own category, then keeps only the number ones:


WITH ranked AS (
  SELECT p.category, p.product_name,
         SUM(s.quantity * s.unit_price) AS revenue,
         RANK() OVER (PARTITION BY p.category
                      ORDER BY SUM(s.quantity * s.unit_price) DESC) AS rnk
  FROM sales s
  JOIN products p ON s.product_id = p.product_id
  GROUP BY p.category, p.product_name
)
SELECT * FROM ranked WHERE rnk = 1;


Module 6Best in each categoryAnswer goes in Checkpoint 10





LAG reaches back to the previous row. Combined with a CTE of monthly
revenue, it gives month-over-month change, the number a manager asks about first:


WITH monthly AS (
  SELECT strftime('%m', sale_date) AS month,
         SUM(quantity * unit_price) AS revenue
  FROM sales
  GROUP BY month
)
SELECT month, revenue,
       revenue - LAG(revenue) OVER (ORDER BY month) AS change
FROM monthly;


Module 6Month over monthAnswer goes in Checkpoint 11
